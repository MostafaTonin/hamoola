# قرار معماري 008 — اعتماد GitHub Actions للتكامل والنشر المستمر (CI/CD)

**الحالة:** معتمد  
**التاريخ:** 2026-09-25

---

## السياق

يحتاج فريق التطوير إلى طريقة آلية للتحقق من جودة الكود، تشغيل الاختبارات، وبناء التطبيقات بدلاً من الاعتماد على الأوامر اليدوية التي قد تُنسى وتتسبب في دمج كود به أخطاء أو لا يعمل (Broken Build) إلى مستودع الكود الرئيسي.

---

## القرار

اعتماد **GitHub Actions** كأداة أساسية لأتمتة عمليات التكامل المستمر (Continuous Integration - CI) والنشر المستمر (Continuous Deployment - CD) في مشروع حمولة.

---

## ما هي GitHub Actions ولماذا؟

- **GitHub Actions ليست بيئة استضافة (لا Staging ولا Production).**
- هي خدمة أتمتة (Automation Workflow) متكاملة مع GitHub، تقوم بتشغيل سكربتات (أوامر) مجدولة أو عند حدوث أحداث معينة (مثل فتح Pull Request أو دمج كود).
- **المشكلة التي تحلها:** تضمن أن الكود المرفوع نظيف، يجتاز كل الاختبارات، وقابل للبناء بدون أخطاء بشرية.

---

## التطبيق العملي للقرار

### 1. المرحلة الحالية (تطوير الـ Frontend فقط)

في هذه المرحلة، ستتكفل GitHub Actions بتشغيل الفحوصات الأساسية لتطبيق Flutter فقط، ويُشترط نجاحها لدمج أي Pull Request:
- تشغيل أداة التحليل `flutter analyze` لضمان خلو الكود من الأخطاء التحذيرية وقواعد التنسيق.
- تشغيل الاختبارات `flutter test` للتحقق من سلامة المكونات والشاشات التي تم بناؤها.
- التحقق من القدرة على البناء (Build Check) للتأكد من أن التطبيق يترجم (Compiles) بشكل صحيح.

### 2. المرحلة اللاحقة (عند إضافة Backend وتهيئة البيئات)

ستتوسع مهام GitHub Actions لتشمل:
- **التكامل (CI):** بناء واختبار الـ Backend (ASP.NET Core) إلى جانب الـ Frontend (Flutter & Web).
- **تجهيز المخرجات (Artifacts):** توليد ملفات البناء النهائية (مثل AAB للموبايل، وملفات النشر للويب والـ Backend).
- **النشر إلى Staging (CD):** أتمتة رفع المخرجات ونشرها إلى بيئة Staging لاختبارها بمجرد الدمج في `main`.
- **النشر إلى Production (CD):** أتمتة تجهيز النشر إلى بيئة الإنتاج، ولكن بشكل محكوم يخضع للموافقة اليدوية (Manual Approval) وفق سياسة المشروع.

---

## الآثار والنتائج

- لا يتم دمج أي Pull Request إلى الفروع الرئيسية (مثل `main`) إلا بعد أن يمر بنجاح بجميع الفحوصات (Status Checks) الخاصة بالـ CI في GitHub Actions.
- **في الوقت الحالي:** هذا توثيق للقرار فقط، ولن يتم إنشاء ملفات `workflows` فعلية أو إضافة إعدادات الـ CI/CD إلى الكود إلا عند بدء مرحلة إعداد البيئة الآلية.

---

## البدائل التي تمت مناقشتها

- **Bitbucket Pipelines / GitLab CI:** بدائل جيدة ولكننا نستخدم GitHub كمستودع أساسي للكود، لذا GitHub Actions هو الخيار الطبيعي والأكثر تكاملاً (Native Integration).
- **Jenkins:** أداة قوية ولكنها تتطلب استضافة خاصة وإدارة للسيرفر، مما يضيف تعقيداً غير مبرر للفريق في هذه المرحلة مقارنة بـ GitHub Actions المدارة بالكامل.

---

## ملاحظات أو قيود

- يتطلب إعداد GitHub Actions لاحقاً فهم وإعداد الأسرار (Secrets) للاتصال بخوادم الـ Staging والـ Production بشكل آمن دون تسريبها في مستودع الكود.
- سيتم البدء بتنفيذ وتفعيل هذه الأتمتة لاحقاً بشكل مستقل؛ هذا التوثيق يثبت القاعدة كمرجعية للفريق.

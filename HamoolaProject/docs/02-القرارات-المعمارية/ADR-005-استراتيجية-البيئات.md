# قرار معماري 005 — استراتيجية البيئات

**الحالة:** معتمد  
**التاريخ:** 2026-09-25

---

## السياق

التطوير الاحترافي يتطلب فصل البيئات لضمان استقرار المنتج وأمان البيانات. الخلط بين بيئات التطوير والاختبار والإنتاج يؤدي إلى مشاكل جسيمة: فقدان بيانات، ظهور أخطاء للمستخدمين، صعوبة التشخيص.

---

## القرار

نعتمد استراتيجية ثلاث بيئات:

```
Local  →  Staging  →  Production
```

---

## تفاصيل كل بيئة

### 1. Local (بيئة التطوير المحلية)

| العنصر | التفاصيل |
|---|---|
| **المستخدمون** | المطورون فقط |
| **قاعدة البيانات** | قاعدة بيانات محلية على جهاز المطور |
| **البيانات** | بيانات تجريبية يصنعها المطور يدوياً |
| **الـAPI** | يعمل على `localhost` |
| **الهدف** | التطوير السريع واختبار الميزات الجديدة |
| **الاستقرار** | لا يُشترط — يتوقع الانهيار والتجريب |

---

### 2. Staging (بيئة الاختبار / ما قبل الإنتاج)

| العنصر | التفاصيل |
|---|---|
| **المستخدمون** | فريق التطوير، فريق الاختبار (QA)، العميل لمراجعة الـFeatures |
| **قاعدة البيانات** | قاعدة بيانات مستقلة على سيرفر Staging |
| **البيانات** | بيانات تجريبية منظمة (Seed Data) — **ليست بيانات حقيقية** |
| **الـAPI** | يعمل على سيرفر Staging مخصص |
| **الهدف** | اختبار الميزات في بيئة شبيهة بالإنتاج |
| **الاستقرار** | يُشترط نسبياً — يجب أن يعمل بشكل سليم للاختبار |

> **Staging ليست للمستخدمين الحقيقيين.** هي بيئة تشبه Production لكن تستخدم بيانات وهمية.

---

### 3. Production (بيئة الإنتاج)

| العنصر | التفاصيل |
|---|---|
| **المستخدمون** | المستخدمون الحقيقيون (عند الإطلاق الرسمي) |
| **قاعدة البيانات** | قاعدة بيانات إنتاج مع نسخ احتياطية (Backups) |
| **البيانات** | بيانات حقيقية للمستخدمين — **تُعامَل بحماية قصوى** |
| **الـAPI** | سيرفر إنتاج عالي الأداء |
| **الهدف** | خدمة المستخدمين الحقيقيين |
| **الاستقرار** | ضروري — أي انهيار يؤثر على المستخدمين |

> **Production الحالية ليست بيئة إطلاق تجاري** — هي بيئة مستهدفة مستقبلاً عند اكتمال المشروع.

---

## قواعد صارمة

1. **❌ لا يتم خلط قواعد البيانات بين البيئات أبداً.**
2. **❌ لا تُستخدم بيانات Production في التطوير أو الاختبار.**
3. **❌ لا تُنشر ميزة على Production مباشرة دون المرور بـStaging.**
4. **✅ كل بيئة لها ملف إعداد (Configuration) مستقل.**
5. **✅ بيانات الاعتماد (Credentials) لكل بيئة مختلفة ومعزولة.**

---

## كيف تنتقل Feature من بيئة إلى أخرى؟

```
1. المطور ينفذ الـFeature على بيئة Local
      ↓
2. يفتح Pull Request على GitHub
      ↓
3. مراجعة الكود (Code Review)
      ↓
4. يُدمج في الـBranch الرئيسية
      ↓
5. يُنشر تلقائياً على Staging (عبر CI/CD)
      ↓
6. اختبار على Staging (QA أو العميل)
      ↓
7. موافقة على النشر لـProduction
      ↓
8. يُنشر على Production (عبر CI/CD بعد الموافقة)
```

## ملاحظات مستقبلية

- إضافة بيئة **UAT (User Acceptance Testing)** تكون بعد Staging وقبل Production عند الحاجة.
- تفاصيل إعداد الـConfiguration لكل بيئة موثقة في `docs/04-البيئات-والنشر/`.

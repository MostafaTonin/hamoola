# دورة نشر تطبيق الموبايل — Flutter

**تاريخ الإنشاء:** 2026-09-25  
**آخر تعديل:** 2026-09-25  
**الحالة:** معتمد (المفاهيم والمسار العام)، قيد الدراسة (تفاصيل الاستضافة)

---

## الهدف من هذه الوثيقة

هذه الوثيقة ليست فقط عن كيفية رفع التطبيق إلى Google Play.

الهدف الحقيقي هو أن يفهم كل عضو في الفريق العلاقة الكاملة بين:

```
Flutter App
    ↓
  Build
    ↓
APK / AAB
    ↓
Google Play
    ↓
Staging / Production
    ↓
Backend API (ASP.NET Core)
    ↓
Database (Relational Database المركزية)
```

هذا الفهم ضروري لأن أخطاء شائعة تحدث عندما يخلط أعضاء الفريق بين دور Google Play ودور الـBackend ودور قاعدة البيانات.

---

## المفهوم الأساسي: ثلاثة مكوّنات مستقلة

من أهم المفاهيم التي يجب فهمها قبل أي حديث عن النشر:

### المكوّن الأول: تطبيق الموبايل (Flutter Application)

- هو الواجهة التي يراها المستخدم ويتفاعل معها.
- يعمل على جهاز المستخدم (هاتف iOS أو Android).
- يُوزَّع عبر **Google Play** (Android) أو **App Store** (iOS).
- **هو Client فقط** — لا يخزن بيانات النظام، لا يشغّل Business Logic معقدة.

### المكوّن الثاني: Backend (ASP.NET Core API)

- هو المحرك الخفي لكل العمليات التجارية.
- يعمل على **Server / Cloud** مستقل تماماً عن Google Play.
- يتلقى طلبات من التطبيق عبر **HTTPS**.
- يُطبّق قواعد الأعمال (Business Logic).
- يتحدث مع قاعدة البيانات.

### المكوّن الثالث: Database (قاعدة البيانات المركزية)

- تعمل على **Server مستقل** أيضاً.
- هي المصدر الوحيد للحقيقة (Single Source of Truth).
- لا يصل إليها التطبيق مباشرة أبداً — فقط عبر الـAPI.

### الصورة الكاملة

```
[هاتف المستخدم]
   Flutter App
       ↓ HTTPS
[Server / Cloud]
   ASP.NET Core API
       ↓
[Server / Cloud]
   Relational Database
```

> **Google Play لا يستضيف الـBackend أو Database.**  
> Google Play وظيفته الوحيدة: **توزيع ملف التطبيق (APK/AAB) على هواتف المستخدمين.**

## مثال تعليمي: تطبيق Flutter مستقل يستخدم SQLite فقط

قبل أن نشرح حمولة، لنفهم مثالاً أبسط يوضح SQLite:

### السيناريو

تطبيق لتدوين الملاحظات (Note-taking App) لا يحتاج اتصالاً بإنترنت.

```
[هاتف المستخدم]
   Flutter App
       ↓
   SQLite
       ↓
بيانات مخزنة محلياً
على نفس الجهاز
```

**في هذا المثال:**
- SQLite موجودة **داخل جهاز المستخدم فقط**.
- كل جهاز لديه نسخته المستقلة من SQLite وبياناته.
- لا يوجد Backend Server.
- لا توجد قاعدة بيانات مركزية مشتركة.
- Google Play يوزع التطبيق على الهواتف فقط — **لا يستضيف SQLite**.
- نشر التطبيق على Google Play لا يعني "نشر SQLite على Google Play" — SQLite تعيش على جهاز المستخدم.

### كيف يختلف هذا عن حمولة؟

| العنصر | مثال SQLite المستقل | حمولة |
|---|---|---|
| تخزين البيانات | داخل جهاز المستخدم | Server مركزي مشترك |
| قاعدة البيانات | SQLite محلية لكل جهاز | Relational Database مركزية |
| Backend | لا يوجد | ASP.NET Core API |
| الاتصال بالإنترنت | غير ضروري | ضروري |
| مشاركة البيانات | مستحيلة بين الأجهزة | ممكنة عبر الـAPI |
| Google Play | يوزع التطبيق | يوزع التطبيق |

## APK مقابل AAB — الفرق المبسط

| | APK (Android Package) | AAB (Android App Bundle) |
|---|---|---|
| **الاستخدام** | تثبيت مباشر على الجهاز | رفع على Google Play |
| **الحجم** | أكبر (يحتوي كل الـABIs) | أصغر (Google Play يولد APK مناسب لكل جهاز) |
| **التوزيع** | مباشر أو للاختبار الداخلي | Google Play فقط |
| **الموصى به** | للاختبار الداخلي والتوزيع خارج Play | النشر الرسمي على Google Play |

```bash
# بناء APK (للاختبار أو التوزيع المباشر)
flutter build apk --release

# بناء AAB (للرفع على Google Play)
flutter build appbundle --release
```

## دورة نشر Flutter على Google Play — خطوة بخطوة

### الخطوة 1: تجهيز التطبيق

- تحديد **Application ID** (Package Name) المميز:
  ```
  com.hamoola.app
  ```
  > لا يمكن تغيير Application ID بعد النشر الأول على Google Play.

- ضبط **Version** و **Version Code** في `pubspec.yaml`:
  ```yaml
  version: 1.0.0+1
  # الصيغة: versionName+versionCode
  # versionName = ما يراه المستخدم (1.0.0)
  # versionCode = رقم تصاعدي داخلي لـGoogle Play (+1, +2, ...)
  ```

### الخطوة 2: إعداد Release Build

- تأكد أن `--dart-define` يُمرر للبيئة الصحيحة:
  ```bash
  flutter build appbundle --release \
    --dart-define=ENVIRONMENT=production
  ```

### الخطوة 3: App Signing (التوقيع)

- كل تطبيق Android يجب أن يكون **موقعاً (Signed)** بـ Keystore.
- Google Play يدعم **Play App Signing** (يُوصى به) — Google يحتفظ بالـKeystore الرئيسية.
- الـKeystore ملف حساس جداً: **لا يُوضع في Git أبداً**.
- **فقدان الـKeystore يعني عدم القدرة على نشر تحديثات للتطبيق**.

### الخطوة 4: حساب Google Play Developer

- يُنشأ مرة واحدة على: [play.google.com/console](https://play.google.com/console)
- **رسوم التسجيل:** رسوم لمرة واحدة (تحقق من السياسة الحالية لـGoogle Play وقت التسجيل — الأرقام تتغير).
- رسوم Google Play هي رسوم تسجيل فقط — **لا رسوم شهرية لاستضافة التطبيق**.

### الخطوة 5: إنشاء التطبيق في Google Play Console

- إنشاء التطبيق وملء بيانات Store Listing:
  - اسم التطبيق.
  - وصف قصير وطويل.
  - لقطات شاشة (Screenshots).
  - أيقونة التطبيق.
  - فئة التطبيق.

### الخطوة 6: متطلبات Google Play الإلزامية

> **مهم:** متطلبات Google Play تتغير باستمرار. راجع **Google Play Console** وقت التنفيذ الفعلي للاطلاع على أحدث المتطلبات.

المتطلبات الشائعة حالياً:
- **Privacy Policy**: صفحة ويب توضح كيفية استخدام بيانات المستخدمين.
- **Data Safety**: إعلان عن البيانات التي يجمعها التطبيق وكيف يستخدمها.
- **Target API Level**: يجب أن يستهدف التطبيق الإصدار المحدد من Android API.

### الخطوة 7: رفع AAB

```bash
# بناء AAB أولاً
flutter build appbundle --release

# الملف الناتج في:
# build/app/outputs/bundle/release/app-release.aab
```

ثم رفع الملف عبر Google Play Console.

### الخطوة 8: Testing Tracks

## Google Play Testing Tracks

Google Play يوفر مسارات اختبار تدريجية:

```
Internal Testing
      ↓
Closed Testing
      ↓
Production
```

### Internal Testing (الاختبار الداخلي)

- **من يستخدمه:** فريق التطوير والاختبار (حد أقصى 100 مختبر).
- **الهدف:** اختبار سريع داخلياً.
- **الوصول:** فوري تقريباً بعد الرفع.
- **في حمولة:** نستخدمه لاختبار Staging Build على هواتف الفريق.

### Closed Testing (الاختبار المغلق)

- **من يستخدمه:** مجموعة اختبار محددة (Early Adopters / Beta).
- **الهدف:** اختبار أوسع قبل الإطلاق العام.
- **في حمولة:** يمكن استخدامه لاختبار مع مجموعة محدودة من المستخدمين الحقيقيين.

### Production

- **من يستخدمه:** جميع المستخدمين.
- **الهدف:** الإطلاق الرسمي.
- **في حمولة:** يُستخدم عند اكتمال المشروع وجاهزيته الكاملة.

> **ملاحظة:** متطلبات كل مسار وإجراءاته قد تتغير. راجع Google Play Console وقت التنفيذ.

## ما الذي ندفع مقابله؟

هذا جدول يوضح بنود التكاليف المتوقعة:

| البند | من يدفع مقابله؟ | ملاحظة |
|---|---|---|
| **Google Play Developer Account** | رسوم تسجيل لمرة واحدة | تحقق من السياسة الحالية |
| **Google Play عمولة المبيعات** | نسبة من إيرادات التطبيق المدفوع | لا ينطبق إذا التطبيق مجاني |
| **استضافة Backend (ASP.NET Core)** | شهرياً — Cloud Provider أو VPS | قيد الدراسة |
| **استضافة Database** | شهرياً — Managed أو Self-hosted | قيد الدراسة |
| **Domain** | سنوياً | للـAPI URL |
| **SSL Certificate** | مجاناً (Let's Encrypt) أو مدفوع | للـHTTPS |
| **خدمات خارجية (Maps, Push, إلخ)** | حسب الخدمة | قيد الدراسة |

> **Google Play لا يفرض رسوم شهرية لاستضافة التطبيق نفسه.**  
> رسوم الاستضافة الشهرية تخص Backend وDatabase — وهي منفصلة تماماً عن Google Play.  
> **جميع الأرقام المالية يجب التحقق منها وقت التنفيذ الفعلي — فهي تتغير.**

## Staging لتطبيق الموبايل

Staging ليست مجرد نسخة من الكود — هي **نسخة تشغيلية كاملة** مهيأة للاتصال ببيئة Staging.

```
[هاتف الفريق]
  Flutter Staging Build
       ↓ HTTPS
[Staging Server]
  Staging API (ASP.NET Core)
       ↓
[Staging Database]
  بيانات تجريبية
```

**بيانات Staging:**
- مستخدمون تجريبيون مصطنعون.
- طلبات نقل وهمية.
- حمولات تجريبية.
- **لا توجد بيانات مستخدمين حقيقيين في Staging أبداً.**

**كيف يتصل التطبيق بـStaging وليس Production؟**

```dart
// يتم تمرير البيئة وقت البناء:
// flutter build apk --dart-define=ENVIRONMENT=staging

const String environment = String.fromEnvironment(
  'ENVIRONMENT',
  defaultValue: 'local',
);

const String apiBaseUrl = environment == 'production'
  ? 'https://api.hamoola.com'
  : environment == 'staging'
    ? 'https://staging-api.hamoola.com'
    : 'http://localhost:5000';
```

> **ملاحظة:** تنفيذ Environment Configuration الكامل في Flutter سيُوثق منفصلاً عند التطبيق الفعلي.

## Production لتطبيق الموبايل

```
[هاتف المستخدم الحقيقي]
  Flutter Production Build
       ↓ HTTPS
[Production Server]
  Production API (ASP.NET Core)
       ↓
[Production Database]
  بيانات حقيقية — تُعامَل بحماية قصوى
```

**مسار الإطلاق التجاري:**

```
Production Build
      ↓
Google Play Console
      ↓
Production Track
      ↓
Google Play للمستخدمين
      ↓
المستخدم يثبت التطبيق
      ↓
يتصل بـProduction API
      ↓
يتصل بـProduction Database
```

> **Google Play يوزع التطبيق. الـBackend والـDatabase يعملان على Server مستقل.**

## كيف يختبر الفريق Staging على الهواتف؟

هذا هو المسار الذي نريد تطبيقه في حمولة:

```
المطور يكمل الـFeature
      ↓
GitHub (Pull Request + Merge)
      ↓
CI/CD (GitHub Actions)
      ↓
بناء Staging AAB تلقائياً
      ↓
رفع على Google Play Internal Testing
      ↓
أعضاء الفريق المدرجون في Internal Testing
      ↓
تثبيت التحديث على هواتفهم
      ↓
اختبار التطبيق
      ↓
يتصل بـStaging API
      ↓
يتصل بـStaging Database
```

**هذا المسار يسمح للفريق بـ:**
- اختبار التطبيق على أجهزة حقيقية لا على Emulator فقط.
- اكتشاف مشاكل الأداء والتوافق مبكراً.
- اختبار سلوك التطبيق مع بيانات Staging الواقعية.

## Environment Configuration — مبادئ أساسية

**قاعدة:** لا يجوز وجود URL ثابت لـProduction مضمّن في الكود بطريقة لا يمكن تغييرها.

| البيئة | API Base URL | قاعدة البيانات |
|---|---|---|
| Local | `http://localhost:5000` | Local Database |
| Staging | `https://staging-api.hamoola.com` | Staging Database |
| Production | `https://api.hamoola.com` | Production Database |

**قواعد Configuration:**

1. **لا Secrets داخل Flutter Application** — أي بيانات حساسة تبقى في الـBackend.
2. **URL الـAPI قابل للتغيير** حسب البيئة وقت البناء.
3. **لا تستخدم Production URL في بناء Staging** — هذا خطأ جسيم يربك البيانات.

## SQLite في حمولة — الموقف الرسمي

| الموقف | التفاصيل |
|---|---|
| **SQLite ليست قاعدة البيانات المركزية لحمولة** | القرار معتمد |
| **القاعدة المركزية** | Relational Database خلف ASP.NET Core API |
| **SQLite مسموح بها لاستخدامات محددة** | Cache، Drafts، Offline Data محدودة |
| **SQLite مصدر الحقيقة الرئيسي** | مرفوض |

**حالات الاستخدام المسموحة مستقبلاً:**

```
✅ تخزين بيانات Cache لتسريع التحميل
✅ حفظ مسودة طلب نقل لم يُرسَل بعد
✅ بيانات Offline محدودة مع مزامنة لاحقة
✅ إعدادات تفضيلات المستخدم
❌ قاعدة البيانات الرئيسية للنظام
❌ مصدر البيانات بديلاً عن الـAPI
```

## ما الذي سنطبقه فعلياً في حمولة؟

هذا هو المسار المخطط للمشروع بالترتيب:

| المرحلة | ما يتم | الحالة |
|---|---|---|
| **1. التطوير المحلي** | كل مطور يعمل على Local مع Local API | جارٍ حالياً |
| **2. إعداد Staging Environment** | سيرفر Staging + Staging API + Staging Database | قيد الدراسة |
| **3. Staging Flutter Build** | بناء تلقائي عبر CI/CD يستهدف Staging API | قيد الدراسة |
| **4. توزيع Staging على الفريق** | Google Play Internal Testing أو توزيع APK مباشر | قيد الدراسة |
| **5. الاختبار على أجهزة حقيقية** | فريق الاختبار يختبر على هواتفهم | مستقبلاً |
| **6. الاتصال بـStaging API/Database** | التحقق من سلوك التطبيق مع بيانات تجريبية | مستقبلاً |
| **7. Production Build** | عند اكتمال الميزات واعتمادها | مستقبلاً |
| **8. Google Play Production Release** | الإطلاق التجاري الرسمي للمستخدمين | مستقبلاً |

> **Google Play App Signing** و **Keystore** و **Application ID النهائي** ستُحدد وتُوثق في وثيقة مستقلة عند بدء مرحلة التحضير للنشر الفعلي.

## ملاحظة ختامية

هذه الوثيقة تصف **المبادئ والمسار العام** لدورة نشر تطبيق الموبايل في حمولة.

**ما هو قيد الدراسة ولم يُحسم بعد:**
- Cloud Provider لاستضافة Backend وDatabase.
- الأدوات المحددة لـCI/CD Pipeline.
- آلية توزيع Staging (Google Play Internal Testing مقابل توزيع APK مباشر).
- تفاصيل App Signing والـKeystore.

**الأرقام المالية وبنود تكاليف Google Play يجب مراجعتها مباشرة من Google Play Console وقت التنفيذ الفعلي، إذ تتغير هذه الأرقام بمرور الوقت.**

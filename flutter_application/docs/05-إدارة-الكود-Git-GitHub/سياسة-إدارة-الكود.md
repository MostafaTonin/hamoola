# 05 — إدارة الكود: Git و GitHub

**تاريخ الإنشاء:** 2026-09-25  
**آخر تعديل:** 2026-09-25  
**الحالة:** معتمد

---

## الاستراتيجية المعتمدة: GitHub Flow المنظّم

نعتمد **GitHub Flow** كاستراتيجية أساسية لإدارة الكود. هو أبسط من GitFlow ومناسب لفريق صغير يعمل بشكل متواصل.

> **لا نطبق GitFlow الكامل** (develop / release / hotfix branches) إلا إذا ظهر احتياج حقيقي موثق.

---

## هيكل Branches

```
main                    ← الكود المعتمد الجاهز للنشر
│
├── feature/xxx         ← تطوير ميزة جديدة
├── fix/xxx             ← إصلاح خطأ (Bug Fix)
└── docs/xxx            ← تحديث التوثيق فقط
```

### main Branch

- **الكود الموجود على `main` دائماً جاهز للنشر** (أو في حالة استقرار كاملة).
- **❌ لا يعمل أحد مباشرة على `main` أبداً.**
- **✅ `main` محمية** — كل تغيير يمر عبر Pull Request.
- **✅ كل Merge على `main` يُشغل CI Pipeline** تلقائياً.

---

## قواعد تسمية Branches

| النوع | الصيغة | مثال |
|---|---|---|
| ميزة جديدة | `feature/اسم-الميزة` | `feature/splash-screen` |
| إصلاح خطأ | `fix/وصف-الخطأ` | `fix/onboarding-navigation-crash` |
| تحديث توثيق | `docs/اسم-الوثيقة` | `docs/naming-conventions` |
| تحسين أداء | `perf/اسم-التحسين` | `perf/image-loading-optimization` |
| تحسين كود | `refactor/اسم-التحسين` | `refactor/auth-bloc` |

### قواعد التسمية

- **حروف صغيرة فقط** (lowercase).
- **كلمات مفصولة بـ `-`** (kebab-case).
- **وصف مختصر ودال** على محتوى الـBranch.
- **لا تضع رقم Issue دون وصف** — مثال خاطئ: `feature/issue-42`، صحيح: `feature/issue-42-driver-profile`.

---

## قواعد Commit Messages

نتبع نمط **Conventional Commits** (https://www.conventionalcommits.org):

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### أنواع الـCommits (Type)

| النوع | الاستخدام |
|---|---|
| `feat` | إضافة ميزة جديدة |
| `fix` | إصلاح خطأ |
| `docs` | تحديث التوثيق فقط |
| `style` | تغييرات في التنسيق لا تؤثر على المنطق |
| `refactor` | إعادة هيكلة الكود دون تغيير سلوكه |
| `test` | إضافة أو تعديل اختبارات |
| `chore` | تحديث أدوات أو Dependencies |
| `perf` | تحسين الأداء |

### أمثلة صحيحة

```
feat(onboarding): add splash screen with animation
fix(router): resolve navigation crash on back press
docs(adr): add ADR-001 for mobile technology decision
test(splash): add widget test for splash screen rendering
refactor(auth-bloc): simplify state emission logic
chore(deps): update go_router to 14.8.1
```

### أمثلة خاطئة

```
❌ update
❌ fix bug
❌ WIP
❌ تعديل الشاشة
❌ changes
```

## Pull Requests (PRs)

### متى تفتح PR؟

افتح PR عندما تنتهي من الميزة أو الإصلاح وتريد دمجه في `main`.

### قواعد الـPR

1. **عنوان الـPR** يتبع نفس نمط Commit Message.
2. **وصف الـPR** يشرح:
   - ماذا تم تنفيذه.
   - لماذا (إذا كان غير واضح).
   - كيفية الاختبار.
3. **لا يُدمج PR** يحتوي على Tests فاشلة.
4. **Code Review** مطلوب — على الأقل شخص آخر يراجع الكود.
5. **PR صغير أفضل من PR كبير** — قسّم الميزات الكبيرة إلى PRs أصغر.

---

## Code Review

- **كل PR يحتاج مراجعة** من عضو آخر في الفريق.
- المراجع يتحقق من:
  - صحة المنطق.
  - التزام الكود بمعايير المشروع.
  - وجود Tests كافية.
  - التوثيق إذا كان هناك قرار جديد.
- **التعليقات تكون بنّاءة** وتشرح السبب لا تأمر فقط.

---

## CI (Continuous Integration)

عند كل Push أو PR يتم تشغيل:

1. `flutter pub get` — التحقق من Dependencies.
2. `flutter analyze` — فحص جودة الكود.
3. `flutter test` — تشغيل جميع Tests.

**إذا فشل أي خطوة، لا يُدمج الـPR.**

---

## حماية `main`

- **Branch Protection Rules** مفعّلة على GitHub:
  - يُشترط اجتياز CI قبل Merge.
  - يُشترط موافقة Reviewer واحد على الأقل.
  - ❌ لا يُسمح بـForce Push على `main`.
  - ❌ لا يُسمح بـDirect Push على `main`.

---

## Merge Strategy

- نستخدم **Squash and Merge** لـFeature branches — يجمع كل Commits في الـFeature في Commit واحد نظيف على `main`.
- نستخدم **Merge Commit** للـHotfixes إذا احتجنا لتتبع التاريخ بدقة.

---

## ما لا نفعله

```
❌ العمل مباشرة على main
❌ Commit بعنوان مبهم مثل "fix" أو "update"
❌ Merge PR بدون Code Review
❌ Merge PR مع Tests فاشلة
❌ Squash تاريخ Commits المهمة دون سبب
❌ حفظ Secrets أو Passwords في Git
```
